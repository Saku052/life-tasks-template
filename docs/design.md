# 設計メモ

なぜこの形にしたか。運用してみて壊れた箇所と、その対処を残す。

## 解きたかった問題

タスク管理ツールは3日で使わなくなる。原因はツールの機能ではなく、**入力と更新のコスト**にある。

- 起票が面倒 → メモアプリに逃げる → 一元管理が崩れる
- 状態の更新が面倒 → ボードが実態とずれる → ボードを見なくなる → 死ぬ

なので設計目標を2つに絞った。

1. **起票は一言で済むこと。** 「8/30までにA社のESを出す」でIssueが完成する
2. **状態が実態とずれないこと。** ずれる余地のある操作を潰す

## なぜ GitHub Issues + Projects なのか

専用のタスク管理SaaSではなくGitHubを選んだ理由。

- **チェックリストが標準で使える。** 「タスクを分解して1つずつ消す」がそのまま表現できる
- **CLI (`gh`) がある。** 自動化の対象にできる。SaaSのAPIより手元から叩きやすい
- **開発のタスクと生活のタスクを同じ場所に置ける。** 文脈スイッチの回数が減る
- **無料で、消えない。** 個人開発のサービスは畳まれるが、これは当分残る

## ステータスを4つに絞った理由

`To do` / `Pending` / `In progress` / `Done` の4つだけ。「今週」「今月」のような
**時間軸の列は作らない**。作ると、期限が動くたびにカードを移す作業が発生し、
それをやらなくなった瞬間にボードが嘘をつき始める。

時間軸は Projects の `Due` フィールドが持つ。列は「手の動き」だけを表す。

`Pending` の定義は特に厳しくした。**自分以外の要因で止まっているときだけ**使える。
「なんとなく手が止まった」を Pending に入れられるようにすると、そこがゴミ箱になり、
二度と見返されない。止まったものは To do に戻す。

WIP上限（In progress 5件 / Pending 10件）はシステムでは弾かない。
超えたら警告するだけにしてある。**弾くと、上限を避けるために起票しなくなる**からで、
これは一元管理そのものを壊す。

## すべての操作を `task.sh` に集約した理由

最初は `gh issue` と `gh project item-edit` を直接使っていた。すぐ壊れた。

**Issue の open/close と Project のステータスは別の状態で、片方だけ動く。**
Issue を close しても Project は `In progress` のまま、という状態が普通に起きる。
一度ずれると、ボードとIssue一覧のどちらが正しいのか分からなくなる。

そこで、状態を動かす操作をすべて `task.sh` の1コマンドに閉じ込めた。

```bash
./scripts/task.sh done 12
# → チェックリストの残りを確認 → Project を Done に → Issue を close
```

CLAUDE.md に「`gh project item-edit` を直接叩かない」と明記してあるのは、
Claude が近道をすると同じずれが再発するため。

## `done` にガードを入れた理由

チェックリストが残っている Issue は `done` で止まる。残項目を表示して判断を仰ぐ。

完了処理が一番「雑にやりたくなる」操作だからで、ここを素通しにすると
「Done になっているが実際は終わっていない」Issue が溜まる。ボードが嘘をつく典型例。

## 判断をプロフィールに追い出した理由

ラベル・優先度・期限の判定ロジックを、スキル（プロンプト）側ではなく
`docs/profile.md` に書いてある。スキルは「profile.md を読んで従え」としか言わない。

- 生活が変われば profile.md の1行を直せばよく、**スキルは触らない**
- 判定の根拠が human-readable なテキストとして残る。なぜP0になったかを後から追える
- 他人が使うときは profile.md を差し替えるだけで済む

固有名詞（サークル名・勤務先・プロダクト名）を対応表に足していくほど精度が上がる。
運用しながら辞書が育つ構造にしてある。

## 期限を「締切の前日」にする

「8/30までに」と言われたら Due は **8/29** にする。締切当日を期限にすると、
当日にトラブルが起きた時点で詰む。1日だけ余裕を持たせるのを既定にした。

推定した場合は Issue の概要に根拠を1行残す
（例:「『今週中』と言われたため金曜を期限に設定」）。
後から見て「なぜこの日付なのか」が分からない期限は、守られない。

## 運用してみて分かったこと

- **5分で終わる用事は Issue にしない。** 起票コストのほうが高い。その場でやる
- **Issue を細かく割りすぎない。** 前提条件はチェックリストの先頭に置く。
  別Issueに切り出すと、ボードが「思いつきリスト」になる
- **`stale` は効く。** 7日動いていないものを並べると、大半は「やらないと決めるべきもの」だった

## 今後の課題

- 定期タスク（`Routine`）の自動再作成がまだ手動
- Projects の `Due` によるソートはボード側の設定に依存していて、CLIから制御できていない
